## Branch Guard for Agent Sessions (10-17)

- **Why**: on 2026-10-17 a second agent session committed into another session's worktree on `master` while that worktree held uncommitted work, and moved `master` past a qualified deployment candidate. Nothing broke, but nothing prevented it either: the branch rules were text only, and only Claude Code's `git push` needed a confirmation.
- **Guard**: tracked `.githooks/pre-commit` (executable), activated by `npm ci` / `npm install` through `prepare` → `scripts/git-guard.js install` (`core.hooksPath=.githooks`; skipped outside a git work tree such as the package builder, never replaces a different configured path). It refuses direct commits on `master`/`main` unless the user explicitly asked for that commit (`CS_ALLOW_MASTER=1` for one command) and commits on any branch other than the worktree's pin (`npm run branch:pin` / `branch:unpin` / `branch:status`, stored per worktree in the git directory); fast-forwards, merges and detached HEADs are unaffected. Tool-agnostic: Claude Code, Kilo and humans all commit through git.
- **Rules**: `master` always releasable, short-lived task branches, one session per worktree per branch with the branch recorded in `ACTIVE_TASKS.md`, a release freeze between qualification and deployment, never `--no-verify` — in the `git-workflow` skill, AGENTS.md (v7.1), `development.md` and `agent-spawning.md`.
- **Verification**: `gitGuard.spec.js` 9 cases drive real commits in throwaway repositories (master refusal and override, feature branch plus fast-forward, detached HEAD, pin mismatch/match/unpin, status, install idempotence, foreign hooks path, no-op outside git); a negative control against an empty hooks directory fails the two refusal cases.
