# Localization and Content Standard

> **Status**: Active
> **Last Updated**: 2026-09-14

---

## Purpose

This standard defines how ChoreStrike handles user-facing text, translations, and localization-related change sets.

Use it whenever you touch:

- Vue components and views
- Pinia stores with user-visible messages
- PHP controllers or services that return translated text
- Translation files in `l10n/`
- Copy that affects tone, accessibility, or family-facing clarity

## Core Rules

- All user-facing UI text must be localized.
- Use `t()` or the equivalent Nextcloud localization helper for every user-visible string.
- Do not introduce hardcoded fallback text in English or German in active UI flows.
- Keep user-facing copy short, clear, and age-appropriate.
- Keep code, comments, documentation, and commit messages in English.
- Update translation artifacts in the same change set when text changes.

## Required Files for Text Changes

When you add or change user-facing text, update:

- `l10n/templates/chorestrike.pot`
- `l10n/en.json`
- `l10n/de.json`

If the touched area also uses PHP `.po` files or other localization assets, update those as required by the active workflow.

## Artifact Workflow (POT + JSON)

1. **Source strings:** frontend `t('chorestrike', '...')`, backend `$this->l->t('...')`. Reuse existing keys; use placeholders instead of concatenated strings — named tokens (`{name}`) on the frontend, printf-positional (`%1$s`) in PHP (see the backend contract below).
2. **POT template:** add every new `msgid` to `l10n/templates/chorestrike.pot` — one entry per unique source key, placeholders exactly as in source.
3. **Locale JSON:** add each new key to both `l10n/de.json` and `l10n/en.json` — key names byte-identical, placeholder tokens identical between languages.
4. **Verify:** `npm run l10n:check-keys` is read-only and checks global JS/Vue/PHP literals, finite dynamic owners, exact POT/EN/DE key sets (including dead keys), and each locale's named/printf placeholders against the source key. Missing POT and empty German values fail.
5. **Regenerate:** `node scripts/check-l10n-keys.js --write` sorts and regenerates all three artifacts deterministically, preserves existing translations, and removes keys with no live owner. New EN literals may use the source; new DE entries remain empty and blocking until real German copy is supplied. Run the read-only gate again; review the artifact diff.

Dynamic owners are `TitleCatalog.php` (packs/tiers), `TaskTemplates.json`
(name/description/instructions), `RoomTypes.json` (defaultName), the exported
`MEDAL_LABELS` map, TaskEditForm's energy/recurrence maps, and TaskService's
date-message map. The exact consuming expressions are registered in the
checker; a new unclassified dynamic `t()` argument fails instead of being
silently omitted. Both existing manual singular/plural branches are owned.
Notification title/pack keys are included, not excluded. Regression tests
live in `tests/unit/scripts/localizationGate.spec.js`; the checked-in artifacts
must equal a second regeneration byte-for-byte. `family-core-ux.spec.ts`
verifies real Nextcloud DE/EN rendering, not a translation mock.

PR gate: all new strings wrapped, keys present in POT + both JSON files, placeholders identical in DE/EN, check passes, relevant unit tests updated. Keep localization commits focused (source changes → POT → JSON → i18n tests → docs).

## Implementation Rules

### Frontend

- Use the Nextcloud localization helper in views, components, composables, and stores.
- Localize error and success messages that can reach users.
- Do not use translated UI strings as the only debugging signal in logs.

### Translation bundle loading (frontend)

`@nextcloud/l10n` (v3) does **not** auto-load an app's translation bundle. If the
bundle is never loaded, `translate()` finds nothing in the global registry and
returns the English source string — so the UI stays English even when the
Nextcloud user language is German. ChoreStrike therefore loads its own bundle at
startup:

- `src/i18n.js` exposes `initI18n()`, which calls `loadTranslations('chorestrike')`.
- `src/main.js` awaits `initI18n()` **before** `app.mount()`, so the first render
  already sees the user's language (no English flash).
- `loadTranslations` is idempotent (cached in the global registry), short-circuits
  for English (the source language), and fetches only the `<lang>.json` matching
  the current user.
- The load is bounded by a timeout (`LOAD_TIMEOUT_MS`) and non-fatal: on timeout
  or fetch failure a warning is logged and the UI renders English source strings
  rather than blocking startup.

When adding a new app entry point or a web worker that renders localized text,
call `initI18n()` (or `loadTranslations`) there too. Do not register hardcoded
per-language bundles with `register()` — that would force one language for all
users.

### Backend

- Use the app localization service for translated response messages.
- Keep machine-readable API fields stable and separate from translated display messages.
- Do not trust client-sent text to already be localized or safe.

### Where `t()` happens — backend error-message contract (CS-PLAN-047)

Every **client-visible** API message must be wrapped in `t()` at the layer that
owns the text. The wrap site depends on how the message reaches the client:

1. **Controller-built responses** (`'message' => ...` literals): controllers
   inject a required, non-nullable `IL10N` and wrap each literal with
   `$this->l->t(...)`.
2. **Service exceptions surfaced verbatim** — services throw
   `\InvalidArgumentException` / `NotFoundException` / `ForbiddenException`
   whose `getMessage()` reaches clients, so the service wraps its own literals:
   inject `IL10N` into the service and throw
   `new \Exception($this->l10n->t('...', [$param]))`. This is required for
   every throw site reachable from a controller catch that surfaces the
   message (`ControllerErrorFormatter::validation($e)`, or
   `safeMessage()`/`forbiddenResponse($e)` for NotFound/Forbidden).
3. **Interpolated values use printf-style positional parameters**
   (`%1$s`, `%2$d`) — verified against Nextcloud stable31 that `t()` runs
   parameters through `vsprintf()`. Never concatenate values into the source
   string; never use named `{tokens}` in PHP (they reach clients
   unsubstituted). Frontend may keep named tokens per its own helper contract.
4. **Before adding a `validation()` catch**, audit every exception message
   that can reach it: only curated, client-safe texts (bounds, ids already
   echoed by design) may surface verbatim.
5. **Exclusions (internal-only, deliberately untranslated):**
   - The generic fallback `'An unexpected error occurred'` in
     `ControllerErrorFormatter::safeMessage()` (**decision D2**): it guards
     genuinely unexpected errors whose detail is hidden and logged
     server-side; policy also recorded in the formatter docblock.
   - IAE messages behind catch-alls that hide them (`safeMessage()`) or
     behind controllers returning a *curated* translated response instead of
     `getMessage()` (e.g. `UserController::updateRole`). Wrap them when their
     path becomes client-visible.
    - Test-mode-only code (`TestController`, `TestDataService`) and the
      `TriggerJobs`/`TestDataSeed` CLI commands. These exclusions are exact
      normalized paths, not a blanket exclusion of similarly named files.

Identity-mock test convention: unit tests stub `IL10N::t` with an identity
callback (`fn ($text) => $text`), so message assertions match the wrapped
**source text including placeholders** (`'Invalid weekday: %1$s'`), not the
substituted output.

## Content Rules

- Prefer simple wording over playful or ambiguous wording in core flows.
- Keep labels and action text consistent across views.
- Avoid sarcasm, blame, or punitive language.
- Make icon-only actions understandable with localized labels or accessible names.

## Validation

After changing localization content, run the relevant validation for the touched area.

Recommended checks:

- `npm run l10n:check-keys`
- relevant unit tests for affected views, stores, or services
